# keyring-bifold — Keyring's core packages (a Bifold fork)

*Repo: [github.com/berkmancenter/keyring-bifold](https://github.com/berkmancenter/keyring-bifold) — npm scope `@bifold/*`. Consumed by [[keyring-wallet]] as the `bifold/` git submodule until **2026-11-22**, when the framework was folded into the wallet repository with its history; the packages now live at `keyring-wallet/packages/*`, and this repo is read-only history (its last commit is #1173, 11-21).*

> **The fold, in one paragraph.** The pointer between the two repos had to be moved by a separate "pin bump" pull request about thirty times between 10-25 and 11-20, every release named two commits, and the install wiring kept a second 1 GB `node_modules`. The *one codebase* plan (accepted 11-20) moved the framework in two steps. Phase 1 (11-22, `7e07bb801`) turned the pointer into a real folder with the same contents and history, and Phase 2 (11-25, `ed88e376b`) made the packages workspaces of one dependency tree and dropped the `bifold/` prefix. Nothing the app does changed. Renaming `@bifold/*` to `@keyring/*` is optional later work. The rest of this page describes the framework as a body of code, wherever it lives.

[[keyring-wallet|Keyring]] was two repositories because its ancestor was. The OpenWallet Foundation's **Bifold** is a framework for building verifiable-credential wallets on React Native and Credo-TS, and a wallet built on it is a thin app over Bifold's `core`. The Berkman Klein Center kept that split: `keyring-wallet/app/` holds the Keyring experience, and this fork holds everything reusable — the screens, the agent, and the three things Keyring added that Bifold never had: peer-to-peer relationship credentials, a witness, and hardware attestation. In the OpenVTC turn of September 2026 it gained a fourth, and through October and November most of the community features (private vetting, rooms, chat, polls, sign-in, the mailbox): a complete Trust Task client that lets a phone act as a [[vta-topology|Personal Network Manager]] over a cloud [[verifiable-trust-agent|VTA]], join a [[verifiable-trust-community|community]] and run the [[peer-identity-vetting|vetting ceremony]] from either seat. Nearly every user-visible feature on the wallet page lives here; the wallet repo mostly carries the pointer.

The history runs back to Indicio's `aries-mobile-agent-react-native` sample (first commit 2020-11-06) through Bifold 3.0.x; the public Keyring import is 2026-04-15, tracking upstream Bifold through credo-ts 0.6.3 and then hopping to the `0.7.1-pr-2704` snapshot that carries DIDComm v2. Of the fork's 3,319 commits, 643 are from September and the first week of October 2026. Commits must be signed and DCO signed-off (09-04).

## The Trust Task client (`core/src/modules/trust-tasks/`)

About 21,000 lines in `module/` at Eucalyptus, about 44,500 by the fold (11-22), and 118 screen files, grown from nothing on 2026-09-15. Two legs with the same shape: **`vtaAgent` / `VtaClient`** is the phone's one session with its own agent (link state machine, key swap and rotation, devices and presence, consent requests pushed to the phone as approver, step-up, approval rules, owner acts behind biometrics), and **`vtiAgent`** is the phone's session with a community as a persona (manifest, join, invitation offers, status lists, notices, inbox, wallet cards). Carriages are pluggable — `DidCommV1Carriage`, `DidCommV2Carriage`, `TspCarriage` — and `VtiMediatorTransport` logs into the Affinidi mediator and resolves DIDs with retry. **`vtiVetting`** (2,400 lines) is both seats of the ceremony "as the reference client does it", citing `openvtc-core/src/vetting/{applicant,vetter,tickets}.rs` by name: applicant `Sent → Accepted → Session → Attested`, vetter `request+ticket → Accepted → Session → CardReceived → Attested`, every peer document opened and verified before it is acted on. `dtgV1Writing` chooses the statement shape per community. Since 10-14/15 `hiddenVettingModules` carries the **private vetting** seats, the applicant's five and the vetter's seven `vta/pcs/*` calls on the agent (see [[peer-identity-vetting]]). October and November added the rooms service and its message cache, `keyring/chat/1.0`, polls with blind tickets, `auth/oob` sign-in, `vta-claim`, `contacts/continuity-check`, "Confirm it's you" (`person/confirm-request/0.1`) and the per-phone DIDComm v2 mailbox, all in the same module. The `screens/` directory is the OpenVTC face of the app: `VtaAgentHome`, `VtaLink`, `VtaCreateAgent`, `VtaDevices`, `VtaRequests`, `VtaAskMe`, `AgentChips`, `VtiJoin`, `VtiInvited`, `VtiCommunity`, `VtiVetting`.

## How the wallet consumed it (until 11-22)

The wallet pinned this repo as a **git submodule** at a SHA (`37f34dc7` on 10-07) and declared the packages as ordinary dependencies at their versions; in development the app's Metro config and jest mappers read `src/` directly, so a core change needed no build, while release bundles used each package's `build/`. Every feature that needed new core therefore landed twice: a PR here, then a `chore/pin-bifold-*` PR in the wallet moving the pointer — there were more than thirty such bumps between 09-22 and 10-07, which is why the wallet's log reads like a mirror of this one. CI here included **`vti-conformance`** (now part of the wallet's CI), which clones the wallet, builds its Rust `card-verify` (and a second copy at VTI `vta-service-v0.47.0`) with `cargo build --locked`, and has upstream's `vta-sdk` judge every Vetting Card and statement Keyring signs.
