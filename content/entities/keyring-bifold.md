# keyring-bifold — Keyring's core packages (a Bifold fork)

*Repo: [github.com/berkmancenter/keyring-bifold](https://github.com/berkmancenter/keyring-bifold) — npm scope `@bifold/*`. Consumed by [[keyring-wallet]] as the `bifold/` git submodule.*

[[keyring-wallet|Keyring]] is two repositories because its ancestor was. The OpenWallet Foundation's **Bifold** is a framework for building verifiable-credential wallets on React Native and Credo-TS, and a wallet built on it is a thin app over Bifold's `core`. The Berkman Klein Center kept that split: `keyring-wallet/app/` holds the Keyring experience, and this fork holds everything reusable — the screens, the agent, and the three things Keyring added that Bifold never had: peer-to-peer relationship credentials, a witness, and hardware attestation. In the OpenVTC turn of September 2026 it gained a fourth: a complete Trust Task client that lets a phone act as a [[vta-topology|Personal Network Manager]] over a cloud [[verifiable-trust-agent|VTA]], join a [[verifiable-trust-community|community]] and run the [[peer-identity-vetting|vetting ceremony]] from either seat. Nearly every user-visible feature on the wallet page lives here; the wallet repo mostly carries the pointer.

The history runs back to Indicio's `aries-mobile-agent-react-native` sample (first commit 2020-11-06) through Bifold 3.0.x; the public Keyring import is 2026-04-15, tracking upstream Bifold through credo-ts 0.6.3 and then hopping to the `0.7.1-pr-2704` snapshot that carries DIDComm v2. Of the fork's 3,319 commits, 643 are from September and the first week of October 2026. Commits must be signed and DCO signed-off (09-04).

## The Trust Task client (`core/src/modules/trust-tasks/`)

About 21,000 lines in `module/` alone, grown from nothing on 2026-09-15. Two legs with the same shape: **`vtaAgent` / `VtaClient`** is the phone's one session with its own agent (link state machine, key swap and rotation, devices and presence, consent requests pushed to the phone as approver, step-up, approval rules, owner acts behind biometrics), and **`vtiAgent`** is the phone's session with a community as a persona (manifest, join, invitation offers, status lists, notices, inbox, wallet cards). Carriages are pluggable — `DidCommV1Carriage`, `DidCommV2Carriage`, `TspCarriage` — and `VtiMediatorTransport` logs into the Affinidi mediator and resolves DIDs with retry. **`vtiVetting`** (2,400 lines) is both seats of the ceremony "as the reference client does it", citing `openvtc-core/src/vetting/{applicant,vetter,tickets}.rs` by name: applicant `Sent → Accepted → Session → Attested`, vetter `request+ticket → Accepted → Session → CardReceived → Attested`, every peer document opened and verified before it is acted on. `dtgV1Writing` chooses the statement shape per community. The `screens/` directory is the OpenVTC face of the app: `VtaAgentHome`, `VtaLink`, `VtaCreateAgent`, `VtaDevices`, `VtaRequests`, `VtaAskMe`, `AgentChips`, `VtiJoin`, `VtiInvited`, `VtiCommunity`, `VtiVetting`.

## How the wallet consumes it

The wallet pins this repo as a **git submodule** at a SHA (`37f34dc7` on 10-07) and declares the packages as ordinary dependencies at their versions; in development the app's Metro config and jest mappers read `src/` directly, so a core change needs no build, while release bundles use each package's `build/`. Every feature that needs new core therefore lands twice: a PR here, then a `chore/pin-bifold-*` PR in the wallet moving the pointer — there were more than thirty such bumps between 09-22 and 10-07, which is why the wallet's log reads like a mirror of this one. CI here includes **`vti-conformance`**, which clones the wallet, builds its Rust `card-verify` (and a second copy at VTI `vta-service-v0.47.0`) with `cargo build --locked`, and has upstream's `vta-sdk` judge every Vetting Card and statement Keyring signs.
