# vta-browser-plugin — the VTA Wallet in the browser

*Repo: [github.com/OpenVTC/vta-browser-plugin](https://github.com/OpenVTC/vta-browser-plugin) — npm scope `@openvtc/pnm-*`*

Passkeys solve *local* authentication; DIDs solve *global* identity; neither alone lets a person log into a third-party website **as the controller of their VTA-held DID**. The browser plugin is the bridge: it proves control of a DID hosted in a remote [[verifiable-trust-agent|VTA]] by performing a passkey ceremony in the browser — no DID private key ever leaves the VTA, and no long-lived bearer token sits in browser storage. Its first milestone (May 2026) enrolled a passkey as an `authentication` verification method in the VTA's [[did-webvh|did:webvh]] document, so any relying party can verify a WebAuthn assertion by DID resolution alone (the server half of that idea is VTI's `vti-webauthn` crate, a DID-VM-resolved assertion verifier).

Since then it has grown into three things in one MV3 extension. The **VTA Wallet**: the browser-resident *Personal Network Manager* (see [[vta-topology]]) that holds holder identities, keeps one persistent mediator inbound session *per onboarded agent*, and renders **consent / step-up approvals** for VTA-gated operations — the in-browser sibling of the iOS mobile agent. The **management console** (September 2026): everything an operator used to do to their agent from the `pnm` CLI — contexts, keys, DIDs, ACL, approvals, policy, transports, audit, and since Eucalyptus the mediator carrying the agent's mail — reachable from a browser tab, composed in the console and signed in the wallet's offscreen document so the console itself holds no key material. And the **persona identity map** (attributes, faces, contexts, contacts, disclosure history) and **data rooms** panes, the first user-facing surfaces for the VTA's persona and rooms task families. At the `VTI-Eucalyptus` tag (2026-10-07) the project's own release arc summed the Dogwood → Eucalyptus window up as "a VTA management console with proof-of-presence step-up, faces manager, rooms, TSP Rev 3 in tsp-js, sign-in over auth/authenticate/0.2" — the first time the plugin carries a *final* coordinated tag since Dogwood ([[coordinated-releases]]).

*Not to be confused with `pnm-server`:* that is the headless build of VTI's Rust `pnm` CLI (secrets in plaintext config rather than an OS keyring), downloaded from `download.firstperson.dev/pnm-server/…` in the [[vti-setup]] guides. Nothing in this repo produces it.

## How the Web Login Family Fits Together

```
web page ──window.vtaWallet.{login | proxyLogin | walletProfile | requestTask | approveStepUp}──▶ extension
   extension ──▶ @openvtc/pnm-core  (Trust-Task envelopes; channel signs every document; origin → RP pin)
      ──▶ @openvtc/vti-tsp-js       (TSP Rev 3 frames; Trust Task inside the tsp/0.1 binding envelope)  ─┐
      ──▶ @openvtc/vti-didcomm-js   (authcrypt, verified sender; routing/2.0 forward; mediator WS)      ─┼──▶ VTA / RP
      ──▶ REST                       ({base}/trust-tasks, the HTTPS binding; net-guard vets the base URL) ─┘
   ◀── every reply's Data Integrity proof verified, its signer checked against the agent addressed (#215),
       and since #278 a reply is believed only from the peer the transport *authenticated*
RP server ──▶ verifies the auth/authenticate/0.2 response (or, for proxyLogin, the id_token) by resolving the persona DID
manager.html ──RUNTIME_MANAGER_TASK / RUNTIME_MEDIATOR──▶ offscreen mints + signs ──▶ same channels (console holds no key)
```

Transport preference is TSP > DIDComm > REST, but since #143 the UI reports the transport that *actually carried a byte* ("advertisement is not availability"). The `vti-didcomm-js` floors are correctness constraints, not preferences: `^0.6.2` for hand-off-then-ack (R1.6), `^0.10.0` for reading long-framed (`--E`) TSP replies, `^0.11.0` for a mediator's own Trust-Task replies to be acked rather than pile up in the holder's queue, and `^0.12.0` for the authenticated `VerifiedSender` the wallet now authorizes on. REST survives Eucalyptus as a *transport* — Trust Tasks posted to `{base}/trust-tasks`, the HTTPS binding — but the bespoke REST endpoints it used to depend on (`/auth/step-up/vta/*`, the SIOPv2 `id_token` envelope) are gone, replaced by Trust Tasks that ride any channel.

Three sign-in shapes, all of which sign in as a **per-site persona** rather than the wallet's own holder DID (#144–#146, VTI-Dogwood): **`login`** — since #284 (09-28) the canonical `auth/challenge` → `auth/authenticate/0.2` pair as Trust Tasks to the RP's `{baseUrl}/trust-tasks`, every reply required to be signed by the RP pinned for that origin; the page may hand over a `did:key` *session key*, which the wallet puts inside the document the subject signs and which the RP must echo, so the page can sign its own session requests afterwards without the wallet (such a sign-in is always asked, even for a remembered site). This **replaced the self-issued SIOPv2 `id_token`**, and the SIOP login client was removed from the extension — the `siop/` module stays in pnm-core only for the vault's `didSelfIssued` entries. **VTA-proxied login** (`proxyLogin({})` resolve-or-bind; `vault/proxy-login/0.1` mints the token with a vault-held key that never leaves the VTA; `walletProfile({target})` answers "who does this site know me as?" without enumerating the vault). **Trust-Task login over the wallet's own transport** (`loginDidcomm`, since #141 the same `auth/*` pair over whichever transport the RP advertises, signed as the persona by `vault/sign-trust-task/0.2`). Around all three sits the **origin → RP pin** (#281, "M5"): a pin is seeded only by a login the human approved, looked up by exact attested origin, and `signTrustTask` / `stepUpVta` refuse any recipient or base URL other than the pinned one.

## Recent Development

- **Eucalyptus final (2026-09-18 → 10-07, 83 commits, #257–#295; tagged `VTI-Eucalyptus` 10-07 at d6df679)** — the three weeks that turned the September console into something a community can govern with. Six threads.
  1. **Faces manager — the persona console completed (#262–#271, 09-19 → 09-23; trust-tasks 0.19.14 → 0.19.20, vta-sdk 0.45.1 → 0.47.0).** The identity map learned the parts of persona the September pass left as SDK calls with no surface: links between faces that no attribute holds (#263); the lifecycle answers — who holds an old value, where an edit landed, what a context may call a face (#264); a face saying which of its names is *its own* (`displayName` slot) and kept old values a pinned face depends on, with `persona/attribute/purge-version` behind a confirmation that says the pinned faces will show nothing (#265); **make a face where it is asked for, retire it, reinstate it, read its history** — `persona/profile/compose` with a per-value correlation check before the write, `usage`, `timeline`, `retire`/`reinstate`, face reach, binding `until` (#268); then contacts (`persona/contact/*`, what others have told the holder), formats (`persona/renderers/list`, "what shape did it leave in") and local faces made inside a context (#270), which claim no provenance (#271). Alongside, the ACL table caught up with vti-common: `key-export` (VTI #1619) and the additive `persona-holder`, and a "Narrow with nothing ticked" that used to send `[]` — which the agent reads as *clear the narrowing*, the whole role — is now refused (#267).
  2. **Mediator Lens and QR (#273–#276, 09-23/24).** A mediator serves its own `messaging/*` operations (statistics, every account's queue, one account's mail, a live traffic monitor) as Trust Tasks addressed to *itself*, and the wallet already holds an authenticated session with it for each agent's inbox — so the console can look inside the relay as the agent's holder with no new socket, no second CORS allowance and no key export. `pnm-core/mediator`, an allow-listed offscreen channel (no `config/patch`, no `message/get`), a per-port monitor lease, a preview-then-confirm purge that refuses a stale plan, and the `vti-didcomm-js` 0.11.0 floor it needed (replies never acked, refusals surfacing as timeouts, monitor batches hitting the persist-before-ack path — all three reproduced against a real mediator). Then **every DID gets a QR button** (#275/#276): the bare DID as UTF-8, level M, black on white in every theme (phone cameras refuse inverted codes), the same encoding as the VTC landing page and `pnm vta qr` — so the [[keyring-wallet|Keyring]] phone wallet, or any wallet, can take a DID by scanning it.
  3. **Verified senders (#278, 09-25; `vti-didcomm-js` 0.12.0).** A task-consent outcome — the message that can raise "The VTA refused your approval" and drop the decision the wallet is waiting on — was believed when its plaintext `from` named *any* enrolled executor. It is now keyed on the sender the transport authenticated (the authcrypt `skid`'s DID, or the sender `unpackInboundTsp` proved), must be the executor the decision was sent to, and that identity is persisted with the pending inbound so an MV3 teardown cannot launder it. `sendAndAwaitReply` takes a required `from` (a thread id is not a secret), and sender keys are matched by exact key id.
  4. **Step-up and sign-in become Trust Tasks (#280–#284, 09-27/28).** `stepUpVta` at a did-hosting relying party is now `auth/step-up/start/0.1` → verify the RP-signed `approve-request/0.3` inside → signed `approve-response/0.5` → `auth/refresh/0.1`, all posted to `{base}/trust-tasks`; the bespoke `/auth/step-up/vta/{start,finish}` paths and their snake_case parsing are gone (#280). What a page can have the wallet sign is bounded — no unaddressed documents, nothing addressed to the holder's own agent, no step-up approve-* (#281), and documents a page asks for are signed for `authentication`, the holder's own request, since the control plane refuses an `assertionMethod` proof on them. Then **`login` over `auth/authenticate/0.2` with a page session key** (#284, above), the SIOP client deleted, and page-signed sign-ins refused.
  5. **Console and onboarding fixes (#282–#290, 09-28 → 10-02).** The printed onboarding grant became `--expires 1h --handoff`: since vta-service #1738 an entry may not write one that outlives it (VTI-ACL-053), so the expiring ephemeral could no longer write the wallet's permanent admin; the one-time hand-off marker (VTI-ACL-054, pnm-cli ≥ 0.25.0) is the VTA's answer (#282). Edit an ACL entry's label and expiry, group a context's access list (#283); grant `persona-holder` in the setup command and read it back (#285); a task the VTA relays onward (did:webvh creates, room key reads, `vault/proxy-login`, `provision/integration`) gets ≥ 80 s — the budget `vta_sdk::budget` derives — instead of the channel's 30 s, which had made a DID "time out" while its create succeeded (#287); `auth/revoke-session/0.2` (VTI #1790); clear a context's DID over `vta/contexts/update-did/1.1` (#288). And `signTrustTask` *as* a VTA-held persona now refuses with `sign-trust-task/as-did-unavailable` instead of silently signing with the holder key behind a `console.warn` (#289), and reaches the VTA over TSP or DIDComm when no REST base is known (#290) — both found wiring the VTC console's wallet-authorized signing-key enrollment (`auth/signing-key/enroll/0.2`).
  6. **A per-community approver (#291–#293, 10-03; trust-tasks 0.23.0).** The wallet half of VTI #1919/#1920: `approverIdentity({audience})` mints one approver `did:key` *per relying party* so communities cannot correlate the user, each sealed under the approver KEK rather than HKDF-derived from one root (a derived key cannot be named without the gesture, and deleting it forgets nothing); `approveStepUp` checks the request names this approver and that `boundTo` equals the recomputed `vtc/step-up/v1` digest, shows the reason, operation and community, takes the biometric, and returns a signed `auth/step-up/approver/attest/0.1`; `approveDecision` vouches for a VTC administrator's `task-consent/decision/0.2` — approve *or* deny — after recomputing the `vta/task-consent/v1` payload digest, refusing on a mismatch before any prompt. Every statement is single-use, pinned to the origin's login, and spent before the matching approve-response is signed. #292 took the generated types for both and raised the trust-tasks floor to the first binding whose `git-ns/activity/list/0.1` schema is satisfiable.
  - Housekeeping: Dependabot bumps (#257–#260, #295: Vite 8.3.1, React 19.3, lucide 1.45), a context delete that shows the subtree it destroys (#257), two startup races (#277), an Approve that could be settled as a Deny by its own window closing (#272).
